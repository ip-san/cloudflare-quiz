# ヒント層の掃引

756問すべてにヒントがある。**層として一度も監査していない**（2026-08-30 時点）。
誤答・正解・図・初級解説は全数監査済みなので、ここが残っている中でいちばん太い。

同日の初級36問では、設問レベルの欠陥5件のうち**3件がヒントの欠陥**だった。

## ヒントの仕事は一つだけ

**選択肢を絞り込ませること。** 知識を教えることでも、設問を要約することでもない。
「これを読んだ結果、選択肢が減るか」だけを見る。

## 見つける型（すべて実測で出たもの）

### H-1 どの選択肢にも等しく当てはまる（`hw-010`）

    設問  Cloudflare Workflows はどのようなサービスですか？
    ヒント「途中で失敗しても最初からやり直しにならない」処理の仕組み
    選択肢A CI/CDパイプラインを、失敗しても続きから再実行できる形で管理する
    選択肢B（正解）失敗しても状態を保ったまま確実に完了まで実行する耐久実行エンジン

ヒントがAにもBにも等しく当てはまり、絞り込みに使えない。

**注意: 語の重なりでは判定できない。** 上の例はAとBが**違う語で同じことを言っている**。
必ず意味で判断すること。

### H-2 設問を言い換えただけ（`lb-008`）

    設問  Geo Steeringと他機能の互換性に関する正しい説明はどれですか
    ヒント 地理的な振り分けと、任意の条件を書けるカスタムルールが、
           うまく共存できるかどうかを考えましょう

「共存できるかを考えましょう」は設問の問い直しで、判断材料が無い。

## H-5 正解の「形」を予告する（`pl-014` / `pl-015`、2026-09-12）

正解だけが**複数の事実を組み合わせた複合選択肢**で、他の3肢が単一の主張になっている設問がある。
そこでヒントが「AとBを分けて整理しましょう」「3種類の上限があります」と**答えの構成を予告**すると、
**中身を知らなくても「2つの要素を持つ肢」「3種類を挙げた肢」を選ぶだけで当たる。**

    pl-015 ヒント「「個数」「1回あたりのサイズ」「1秒あたりの速度」という3種類の上限を整理しましょう」
    正解    Stream/Sink/Pipeline 各20個、ペイロード5MB、レート5MB/秒   ← 3種類すべてを挙げた唯一の肢
    誤答    「上限はない」「レートは50MB/秒」「個数は無制限」          ← どれも1種類だけ

**語も含意も見ていない。肢の形だけを見て当たる。** H-1〜H-4 はどれもこれを捕まえない。

### 直す側と、直さない側

**ヒントが形を予告している分は直せる。** 具体的な数値や事実を1つ述べる形にすれば予告が消える
（pl-015 → 「1回の取り込みリクエストで送れるペイロードは、数MBの規模です」）。

**ただし正解だけが複合である構造そのものは設問層の問題で、ヒントでは直らない。**
ヒントを無くしても「いちばん長い肢・いちばん要素の多い肢が正解」で当たる。
pl-014 はこの型で、ヒントを直しても形の手がかりが残るため**設問層の積み残し**に入れた。

### H-5 の変種: 正解が使う「分類の枠組み」を名指しする（2026-09-14）

正解が2〜3の分類で答えるとき、**ヒントがその分類の枠組みをそのまま名指しする**型がある。

```
dx-014  ヒント「『速さ』を測る指標と、『遅延』を測る指標、『ばらつき』を測る指標は、それぞれ別物だと」
        正解    throughput=速度 / latency=遅延 / jitter=ばらつき の3分類
        → 具体的な数値も定義も知らないまま、「3分類を混同していない肢」を形で選べる
dx-015  「ファイル自体に上限があるもの」と「アップロード上限があるだけのもの」の2分類
dx-017  「何時間分を遡るか」と「いつ諦めるか」の2軸
```

**複合肢の予告（元の H-5）と機構は同じで、予告しているのが「要素の数」ではなく「分類の軸」である。**
別立てにせず H-5 に含める。**見分け方は同じ: ヒントを読んだだけで、中身を知らずに肢を選べるか。**

## 誤答を作り直しても直らない場合がある: 正解そのものが一般知識のとき（2026-09-15）

上の3つの手はどれも**「正解には固有の知識が要る」ことを前提にしている。** 前提が崩れる設問がある。

```
hw-017  検査役が Cloudflare Workflows の仕様を一切意識せず、
        「決済APIの冪等キー」という業界一般の定石だけで解いて正解した。
        **正解肢の内容そのものが一般常識と一致している。**
        → 誤答をどれだけ Cloudflare 固有にしても、正解の識別に一般知識で足りてしまう
```

**誤答の作り直しでは直らない。** 選べる道は2つ:

1. **難易度ラベルを下げる**（上級ではなく中級・初級として扱う）
2. **設問を作り直す**（固有の実装機構を問う形に変える。
   hw-017 なら「冪等性をどう実現するか」ではなく「Workflows のどの機構がそれを保証するか」）

### 見分け方

誤答を仕分ける前に、**正解肢だけを読んで「これは一般的な設計常識から導けるか」を問う。**
導けるなら、誤答をいくら作り直しても上級の設問にはならない。

## 設問層・誤答層は「直せない」ではない。3つの手で全部直った（2026-09-13）

「設問文や選択肢の名前・形だけで答えが決まる」設問を、ヒントでは直らないとして10件ほど積み残していた。
**最終的に全部直った。判定は正しかったが、直せないという判断が誤りだった。**
効いた手は3つで、どれも**誤答の側を作り直す**ものである。

### 手1: 正解と同じ名前を含む誤答を入れる（名前一致を無効化する）

```
r2-009  設問文が「一覧」と言い、正解が `list()`。名前が一致するので中身を知らなくても当たる
        → 正解と同じ `list()` を使うが「メタデータを含まずキーのみ返す」という誤答を追加
          名前の有無では絞り込めず、`R2Object` が何を持つかという知識が要るようになった
wr-010  選択肢が `logs export` / `tail` / `dev --logs` / `deploy --verbose` でコマンド名の意味だけで決まる
        → 同じ `wrangler tail` を使うが「console.log を含まず例外情報のみ」という誤答を追加
```

**名前で決まる設問は、その名前を誤答にも持たせれば決まらなくなる。**

### 手2: 極性をそろえる

```
sc-017  「制限事項として正しいもの」と問い、肯定文3つ・否定文1つ。極性が割れているので形で当たる
        → 4肢すべてを「制限がある」という同じ極性に統一し、それぞれ別の事実を誤らせた
```

### 手3: 1つの軸を複数の軸に分解する

```
pg-015  誤答2つが「対応していない」という同じ主張の重複で、可能／不可能の1軸しかない
        → 「Direct Upload は実在する」前提のうえで、別々の具体的事実（切替可否／ZIP対応／Functions対応）を
          それぞれ誤らせた。ヒントで1つ潰しても他2つが残る
```

### 2×2（正解だけが複合肢のとき）

`sl-018` `pl-014` で使った。本物の要素と作った誤りを組み合わせ、**各要素がちょうど2回ずつ現れる**ようにする。
`pl-014` は文字数差が 37字 → 7字 になり、「いちばん長い肢が正解」の手がかりが消えた。

### 誤答を作り直すときに必ず確かめること

1. **新しい誤答の主張が実は真でないこと。** 真なら正解が2つある設問になる。**最優先**
2. **4肢の文字数と要素数を揃えること。** 形の手がかりを消すのが目的なので、ここが崩れたら意味がない
3. **その肢の `wrongFeedback` も書き直すこと。** 据え置くと、選んでいない話への反論や事実誤りが表示される
4. **解説文に各誤答の否定根拠を足すこと**

## 設問文の前提節も「ヒント」として数えること（2026-09-14）

**ヒントだけを見ていると見落とす。** 設問文の冒頭に付く「〜を踏まえると」「〜を前提として」という節が、
ヒントと同じ働きをしていることがある。

```
em-008  設問文「disposition とは別の軸で情報が付与される仕組みであることを踏まえると」
        → 正解の核心（独立した軸・複数付与できる）を設問文が先に述べている。
          ヒストを直しても、設問文だけで正解に届く
```

**全756問を走査すると28問にこの形があり、28問すべてが上級だった。** 文脈を足して難しくするつもりが、
逆に答えを渡している。`ac-016` と `as-011` も後から同じ指摘を受けており、繰り返し出てくる。

### すべてが有害なわけではない

```
有害  答えの核心を先に述べる（em-008 / em-012）、争点を既定事実にする（em-010）
無害  軸を名指しするだけで方向を与えない（gw-006 / gw-007 / gw-011 / gw-013）
```

**判定は同じ問いでよい。「設問文とヒントを合わせて読んだあと、本物の対抗馬が残るか。」**
ヒント単体で数えると、設問文が先に潰した分を数え落とす。

### 手順

**4肢に当てるとき、設問文の前提節をヒントの一部として一緒に読むこと。**
`quiz-audit` の掃引で「ヒントは健全」と判定しても、設問文が潰していれば設問は壊れている。

## 指し示し型を機械的に切り分ける問い（2026-09-12）

潰す数が1肢でも欠陥のことがある。「教えている」のか「名指しで捨てさせている」だけなのかを分ける問いはこれ:

**ヒントが述べている内容は、正解選択肢の文言または解説文に登場するか。**

- **登場する** → その設問が本来教える内容を教えており、誤答が落ちるのは副産物。**正常。**
- **登場しない** → その誤答を否定するためだけに持ち込まれた単発のトリビア。**指し示し型の欠陥。**

読んだ人が持ち帰るものを見れば分かる。設問の要点を持ち帰るなら正常、無関係な知識を持ち帰るなら欠陥。

### 解説文に「登場する」だけでは足りない。図を見ること（2026-09-13 に追加）

**解説文の末尾に誤答否定のために付け足された一文と、本題として教えている内容は、解説文の中では見分けがつかない。**

    sl-013  ヒント「発行される証明書は Domain Validated(DV) です」
            DV は解説文の末尾に出てくる → 上の問いでは「正常」と出る
            しかし**図は SAN 50個 / ゾーンApex / Enterprise 100枚のみで、DV に一切触れない**

**図（`diagrams`）が扱っていない事実は、その設問が教えたい内容ではない。**
図は記憶に残す要点を選んで作ってあるので、本題と付け足しの区別がそこに出ている。

→ **ヒントの内容が解説文にあっても、図が扱っていなければ指し示し型を疑う。**

### ただし「図が正解そのもの」のときは、軸を外すしかない（2026-09-13 に追加）

この基準を、私がこのセッションで書き換えた72件のヒント全部に当ててみた。**軸から外れて見えたのは2件。
どちらも調べたら妥当だった。**

```
px-010  図「自動エンコードと配信」の中身は H.264 自動エンコード / アダプティブビットレート / 回線に応じ最適版
        → **3項目とも正解肢の内容そのもの。** 軸に乗せると必ず答えを漏らす
        私のヒント（埋め込みは iframe か自前プレーヤー）は軸から外れているが、
        作り物の誤答（専用アプリが要る）だけを潰し、本物2つを残し、何も漏らしていない
px-004  図「トークンの3つの性質」も同様に正解肢の内容そのもの
```

**図が正解肢の内容をそのまま示している設問では、軸に乗った瞬間に漏れる。** その場合は軸から外れてよい。

→ **判定はこう:「軸に乗っていて漏らさないヒントが書けるのに、外している」なら欠陥。**
   `sc-010` がそれだった（設定単位という軸を、方向を断定せずに示せたのに、HTTP の範囲という別の話をしていた）。
   **書けないなら外してよい。** 軸に乗ることが目的ではなく、絞り込ませることが目的である。

### 実測した3件（同じ「1肢だけ潰す」ヒント、判定は別）

```
wr-004  「1インスタンスで使えるメモリは128MBに固定」
        → 「128MB」は正解肢にも解説文にも一度も出てこない。必須キー（name/main/compatibility_date）とは
          無関係で、誤答2の `memory_limit` という語だけを狙って否定している。**欠陥**
mw-014  「リースIPと持ち込みプレフィックスで可否が違う」
        → 解説文に明記されている（この設問が教える3事実の1つ）。**正常**
lb-017  「間隔は秒単位まで自由に詰められない」
        → 正解肢の「最小15秒」と解説文に含まれる。**正常**（実測は2肢潰れ。許容内）
```

**この問いは、自分の修正を検査するときにいちばん効いた。** 数だけ見て「1肢に収めた」と満足していた3件のうち、
1件がトリビアだった。数を合わせることと、教えることは別である。

## 誤答が「判定できない」と思ったら、`wrongFeedback` を見ること（2026-09-13）

ある誤答について「解説文にも図にも根拠が無く、真偽を判定する材料が乏しい」という報告が来た（vp-012 の肢0）。
**その肢の `wrongFeedback` に書いてあった。**

```
肢0  「パブリックインターネット宛には別のバインディングを追加する必要がある」
     wrongFeedback「別のバインディングを追加する必要はありません。同じ VPC Networks バインディングで
                    プライベート・パブリックの両方の宛先にアクセスできます」
```

**`wrongFeedback` は、その肢を選んだ人が実際に読む文である。** 誤答を否定する根拠が置かれる正規の場所で、
解説文と図に加えた**3つ目のチャンネル**として数えること。

- **解説文** … 全員が読む。設問の要点
- **図** … 全員が見る。記憶に残す要点（本題と付け足しの区別がここに出る）
- **`wrongFeedback`** … その誤答を選んだ人だけが読む。誤答ごとの反証

3つとも見て根拠が無ければ、**その誤答は反証されないまま残る**ので報告する価値がある。

## 3つ潰れたとき、原因がヒントでない場合がある（2026-09-12）

**「ヒントが答えを漏らしている」と「誤答がそもそも成り立っていない」は、症状が同じで原因が違う。**
どちらも3肢が落ちる。直す場所が別なので、必ず切り分けること。

### 切り分けの問い

**ヒントを消した状態で、知識のある人はその3肢を即座に捨てられるか。**

- **捨てられる** → 誤答が作り物で、対抗馬になっていない。**ヒントの欠陥ではない。** 誤答層の問題。
- **捨てられない**（もっともらしい誤答で、ヒントの言い回しだけが潰している） → **ヒントの欠陥。**

### 実例

```
lb-005  誤答0（endpoint単位のみ可）と正解2（Pool単位も可）は本当に競る。
        ヒントの言い回しだけが潰していた            → ヒントの欠陥。直した
lb-015  誤答が User-Agent/Referer/Accept、TCPポート/TLS/DNS、IP上位2オクテット/地理/ランダム。
        Session Affinity を知っていれば全部即座に落ちる → 誤答層の問題。ヒントを直しても再発する
wr-005  正解だけが `npm create cloudflare@latest` で、誤答3つは全部 `wrangler ...`。
        「新規作成のツール」に触れる助言はすべて3肢を巻き込む → 誤答層の問題
```

lb-015 と wr-005 は**誤答の作り直しが要る**。ヒントを変えても、意味のある助言にした瞬間に3肢が落ちる。
**ヒント層で直そうとすると、H-2（設問の言い換え）に逃げるしかなくなる。** それは交換であって修正ではない。

### H-4 正解への導出経路を渡す（`kv-008`、2026-09-12）

    設問  `caches.default` でキャッシュしたレスポンスの有効範囲について正しい説明はどれですか
    ヒント Cache APIを呼び出すWorkerはどこで実行されるか、まず思い出してみましょう
    正解  Cache APIはグローバルに利用可能だが、内容は保存が行われたデータセンターの外には複製されない

**語はひとつも重なっていない。** それでも「Worker は1つのデータセンターで動く」→
「だから保存も局所的」という**推論の道筋が、正解そのものの導出経路**になっている。
残り3肢（アカウント全体／オリジンのみ／全世界に複製）はすべてこの一歩で落ちる。

**H-4 は語の照合では絶対に見つからない。** ヒントから出発して、受験者が辿る推論を1〜2歩進めてみて、
その先に正解が現れるなら H-4 である。

**私はこれを2回見逃した。** 一度は「機構を示して導かせる形で教育的」と評価して採用し、
もう一度は助言役も同じ評価をした。**2人が一致しても、4肢に当て直す代わりにはならない。**

### H-3 一般論だけで、選択肢に接続しない（`kv-001`）

    選択肢が Durable Objects / Cache API / D1 / Workers KV の4つの固有名詞のみ
    ヒント「低頻度更新・高頻度読み取り」というワークロードの特性から考えましょう

特性は述べているが、4つのどれがそれに当たるかを判断する材料が無い。
**固有名詞が並ぶ設問では、名前と性質を結ぶ軸を名指しする必要がある。**

（かつて「H-4 正解の位置を外している」として別立てにしていたが、H-3 と同じ
「判断に接続しない」型なのでここに畳んだ。H-4 の名前は下の「導出経路を渡す」型に使う。）

### 線は「本物の対抗馬が残るか」で引く（2026-09-12 に置き換え）

2026-09-09 から「潰した数」（1=正常/2=許容/3=欠陥）と、2026-09-11 の「同じ主題に限る」条件で運用してきた。
**この2つは1つの問いに畳める。** 11 件の判定を当て直して、同じ結論が出ることを確認した。

**手順**

1. 誤答3つを**本物**と**成り立っていないもの**に分ける。
   判定は「**ヒントを消した状態で、知識のある人はこれを即座に捨てるか**」。捨てるなら成り立っていない。
2. 成り立っていない誤答は**数に入れない。ヒントが全部潰してよい。**
3. **ヒントを当てたあと、本物の対抗馬が1つも残らなければ欠陥。**

### 4肢に当てるとき、一段さかのぼって前提を見ること（2026-09-13 に追加）

**ヒントが述べた事実そのものではなく、「その文が真であるために成り立っていないといけないこと」が
他の肢を巻き込む。** 私はこれを5回のうち4回で数え落とした。

```
sp-003  「一部の地域は、収集の対象から外れます」
        → 除外の話をした時点で「既定で収集している」が前提になる
        → 誤答「Freeでは一切利用できない」と誤答「明示的に有効化しない限り無効」の両方と衝突し、
          狙っていない2肢が道連れになる

ru-005  「変更や削除に制約があります」
        → 「削除は自由」と主張する肢は、この一般化と衝突して落ちる
```

**語の重なりを見ても見つからない。** ヒントを読んだ人が次に何を当然のことと受け取るかを書き出してから、
4肢に当てること。

```
wr-015  本物2（CLI か ダッシュボードのみか）。ヒストは作り物2つを潰す → 本物2が残る   正常
wr-008  本物2（`wrangler config --secret` か `wrangler secret put`）→ 2が残る          正常
wr-007  本物1（専用フラグのみで設定ファイル不要）。ヒントがそれを潰す → 0が残る        欠陥
kv-008（旧）本物3（複製範囲の主張が3通り）。ヒントが全部潰す → 0が残る                 欠陥
wr-004  そもそも本物が0（docker/region/secrets はどれも Workers の話でない）           誤答層
```

**なぜ数の規則より良いか**

- 「別製品なら例外」（09-11 の条件）は、**別製品の誤答が「成り立っていないもの」の一例**にすぎない。特別扱いが要らなくなる
- 3つ潰しても正常な場合（作り物3つ）と、1つ潰して欠陥の場合（本物1つを潰す）を、同じ問いで扱える
- **直し方が決まる**。「潰す数を減らす」ではなく「**本物の対抗馬に触れない**」が目標になる

**H-1/H-2/H-3 はこの問いでは捕まらない。** 別に見ること。
lb-005 の「A と B は同じ設定か別の設定か」は本物を1つ残していたが H-2 だった。
**残るかどうか（過剰消去）と、教えているかどうか（内容）は別の軸である。**

### 直すときの目標は「本物に触れないこと」

修正を依頼するとき、かつて「潰す誤答は **1 つまで**」と書いて渡して失敗した（2026-09-11、sl-011）。
1 つ以下にする方法は「軸を出さないこと」しかなく、担当は
「各選択肢を公式ドキュメントと照合しましょう」という**全肢に等しく当てはまるヒント**を書いてきた。
hw-010 の型そのもので、潰す数を下げる代わりにヒントを無内容にしていた。

→ **依頼するときは「本物の対抗馬を1つ以上残すこと」と書く。** 数ではなく、残すべき対象を指定する。
   作り物の誤答をいくつ潰しても構わない、と明示すること。

  sl-011 の最終形: 「証明書の有効期限が近づいたとき、Cloudflare 側から何が届いて何が届かないのかを
  確認してみましょう。」→ 軸は示すが方向を断定しないので誤答0（リマインダーが届く）が残る。

**採った事実は、出どころの文が付けている条件をそのまま保つこと**（2026-09-13）。
`kv-012` で、解説文の「`Cache-Control` が禁じている場合、または大きすぎる場合に413エラーを返す」を
「条件を満たさないときはエラーが返るだけ」と一般化し、**正解の仕組み（Set-Cookie は静かに非キャッシュ、
エラーにならない）と食い違う事実誤りを書いた。** 出どころから採っても、範囲を広げれば別の主張になる。
**「〜の場合に」を「〜のときは」に置き換えないこと。**

**修正案は、解説文か正解選択肢にある事実から採る**（2026-09-12）。新しい事実を持ち込むと
トリビア（wr-004 の「128MB」）か事実誤り（wr-005 で書きかけた「`wrangler init` はフレームワークを扱わない」）になる。

**査読者が一般化した数字（15/18、12/19）をそのまま採用しないこと。まず自分で 3 問を 4 肢に当てる。**

## 報告しないもの

- 難易度が高い、という感想だけのもの（ヒントの欠陥ではない）
- 「もっと親切にできる」という改善案（欠陥ではない）
- 答えを言ってしまっているヒント → これは別の型だが、**見つけたら報告してよい**

## 2×2 と parallel-distractor-tails は構造的にぶつかる（2026-09-15）

`quiz-lint.mjs quality` の `parallel-distractor-tails` は、2×2 で作り直した設問を
ほぼ必ず指摘する。**これは誤検知なので直してはいけない。**

2×2 は要素 Y の2つの値を4肢に2回ずつ配る作りなので、Y が誤りの側の2肢は
語尾まで同じ形になる。cs-018 で実際に確かめた: 語尾を共有するのは選択肢1と3で、
正解0は選択肢2と Y の内容を共有する。**2-2 に割れるだけで、どちらの組が正解かは
語尾からは分からない。** 情報は漏れていない。

直そうとして語尾を散らすと、各要素がちょうど2回ずつ出るという 2×2 の性質が壊れ、
「正解だけが違う形」という元の欠陥に戻る。lint の文言にある
「鏡写しの誤答や値の並列は正常」がこの場合にあたる。

現在この理由で残してよいのは cs-018 / cb-010 / zr-015 / pl-014 / r2-009 / hw-018 / ar-009 / ar-017 / ag-007 の9件。
**件数ではなく「その ID が 2×2 で作り直したものか」で判断すること。**
一覧に無い ID が出たら、2×2 の副作用ではなく本物の欠陥を疑う（厚くする過程で語尾を揃えてしまった場合）。

## 判定は2段で行う（2026-09-15 に担当が定式化）

掃引の担当が、これまで散らばっていた基準を2段にまとめてきた。**この形で運用する。**

  **A（論理）** 現行ヒントを**断定として読み**、本物の対抗馬が1つも残らなければ欠陥。
  **B（語）**   A を通った場合、ヒントの語が**「残った誤答には無く、正解肢にだけ有る」**なら欠陥。

**A と B の両方を通れば健全。** 直さない。

**ヒントが答えの一部を無料で配っていても、対抗馬が残り、語の一意な反響が無ければ直さない。**
「漏れているように見えるか」ではなく、この2段で判定する。

### 線引きが効いた実例（同じバッチの2問）

  `em-009` **欠陥**  ヒントの「別製品の購入は不要」が**正解肢にしか無い言い回し**だった
                    （誤答0は「購入する必要がある」で、言い回しが逆）→ B で落ちる
  `em-017` **健全**  ヒントの語（UI経由/API/件数の上限）が**残る誤答2つの両方に出る**
                    → 反響が無いので据え置き

**B を判定するときは「残った誤答」と比べること。** 全4肢と比べるのではない。
A で落ちた肢に語があっても、その肢はもう選択肢として機能していない。

### `lb-011` 型（括弧のラベル貼り）も B で拾える

ヒントが「より具体的な設定**(個々のEndpoint)**」のように**括弧で言い換えを添える**と、
その語が正解肢にしか無い場合に B へ抵触する。対抗馬が残っていても直す。
