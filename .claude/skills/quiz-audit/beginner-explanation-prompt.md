# 初級問題の解説を初学者の目で読む — レビュアー向け手順

**事実の正誤は見ません。** この層は誤答・正解・解説・図のすべてが全数監査済みで、
`referenceUrl` との照合も終わっています。**docs を引く必要はありません。**

見るのは1点だけです。

> **その解説を読んだ初学者は、置いていかれないか。**

## なぜこれをやるか（実測）

2026-08-30 のプレイテストで、ペルソナごとに結果がはっきり割れました。

| ペルソナ | つまずいた率 |
|---|---|
| reviewer（出典と論理に厳しい査読者） | 0/27 (0%) |
| busy-intermediate（実務者） | 6/52 (12%) |
| **beginner（初学者）** | **8/23 (35%)** |

**正確性の床は上がったのに、初学者は中級者の3倍つまずいている。**
しかもその詰まりは、機械では拾えませんでした。
「初級の解説に出てくる未説明の固有名詞」で引くと **200問中124問**が該当し、
`Worker` `API` `Cloudflare` `wrangler.toml` まで全部拾ってしまいます。
**人が読むしかない層です。**

## 探すもの

### B1. 設問の主題そのものが説明されていない

**最も多い。** 「その機能がどうなったか」だけを述べて、
「その機能が何をするものか」を一度も言わない。

```
ag-006  設問「Universal Endpointの現在の位置づけは？」
        解説は「非推奨です。新規はDynamic Routingを」としか言わない
学習者の声:
  「正解はできたけど、そもそも『Universal Endpoint』が何なのか
    最後まで分からなかった。廃止されたことだけ覚えて終わった感じ」
```

### B2. 初出の語がその場で説明されない

```
ai-002  「バインディング」が設問・選択肢・解説を通じて一度も定義されない
ar-004  `workerd` が説明なく登場。Workersと同じものか別物か分からない
```

**ヒントが「既知の前提」で書かれていないかも見てください。**
`ai-002` のヒントは「**他の**バインディング宣言と同じ構造かどうか」でしたが、
初学者はまだ他の例を見ていないので比較のしようがありません。

### B3. 設問に答えるために要らない語を詰め込んでいる

```
as-001  設問は「有料アドオンか、全プランで使えるか」を聞いている。
        なのに解説が API Discovery・JWT検証・Sequence Analytics・
        Sequence Mitigation・Volumetric Abuse Detection を無説明で列挙
ar-013  設問は「社内メンバーだけに絞るには」という初級の話。
        なのに解説が Bypass / Service Auth / デバイスポスチャ / Zaraz を
        前置きなく畳みかける
```

**設問の難易度と解説の難易度が乖離している**形です。

### B4. 例外や注記が本則との関係なしに置かれている

```
ar-004  末尾に「compatibility_dateが2026-08-04以降なら既定で有効」とだけ書かれ、
        「じゃあ今の自分は書くべきか書かざるべきか」が解決しない
学習者の声:
  「正解の理由は分かったけど、最後の注釈を読んだら
    『え、じゃあ今はもう書かなくていいの？』とまた迷ってしまった」
```

### B5. 解説が図の内容を散文で言い直しているだけ

図が表を持っているのに、解説が同じ数値を並べ直している。
中級者からも「結局どの数字を覚えればいいのか」という声が出ています（`ag-018` / `as-018`）。

### B6. 設問そのものが初級ラベルに見合わない — **ラベルを上げるとは限らない**

解説の書き方ではなく、**設問が前提知識を要求している**型。

```
at-002  選択肢が4つとも TypeScript のコード片
学習者の声:
  「コードの断片を4つ並べられても、どれが正しい書き方なのか
    判断する材料が自分にはない。結局『Agentっぽい名前が入ってるから』で
    選ぶしかなかった」
at-003  `プロパティ` `インスタンス` を知っている前提
  「正解はしたけど理解して選んだ感覚がない」
```

**ここで「初級ラベルが誤りだ」と即断しないこと。**

このコーパスの難易度は**製品カテゴリごとの相対的な位置**で付いている。
`at-*`（Agents）の初級6問には「Agentクラスをどう定義するか」が入るが、
それより基本的な Agents の話題は無い。ラベルを上げると
**そのカテゴリに入口が無くなる。**

代わりにやること: **選択肢を読めなくても判断できる手順をヒントで与える。**

```
at-002 の直し方（ヒント）:
  before  「Agent専用の基底クラスと、ルーティング用の関数が用意されています」
  after   「Agentには専用の親クラスがあり、それを継承して作ります。
            リクエストの振り分けにも専用の関数が1つ用意されていて、
            Worker側はそれを呼ぶだけです。
            **この2つがそろっている選択肢を探しましょう**」
```

コードを読めない学習者にも**探し方**が渡る。
用語（`プロパティ`＝クラスに書いておく設定値、`インスタンス`＝1個分の実体）は
解説側でその場で説明する。

### コード比較の設問は系統的な問題ではなかった（2026-08-30 の測定）

`at-002` / `at-003` で「選択肢が4つともコード片で判断材料が無い」という声が出たので、
初級200問のうち**選択肢がコード片の比較になっているもの**を数えた。**23問（11.5%）。**

扱える規模だったので23問のヒントを全部読んだ結果、**大半は良かった。**
コードを読めなくても選べる「判断の手順」が渡されている:

```
ct-004  「特定の相手と話し続けたい」のか
        「誰でもいいから空いている相手と話したい」のか、という違いを考えましょう
d1-005  「作成」と「適用」で2つの別々のコマンドがあります
cs-004  「このドメインは本当にあなたのものか」の確認と、
        「証明書を発行していいか」の確認は、別々の手続きだと考えましょう
```

**外れ値は `at-002` の1問だけだった:**

```
before  「Agent専用の基底クラスと、ルーティング用の関数が用意されています」
        → 事実を述べているだけで、手順になっていない
```

プレイテスターの観察とも一致する。同じ回で
「as-* / bi-* / bt-* は専門用語がその場で定義されていて概ね良好」と報告があり、
詰まりは `at-*`（Agents）に集中していた。

**したがってコード比較そのものを直す作業は要らない。**
構文を問う設問でコードを並べるのは正当な出題で、
必要なのは「読めなくても選べる手順」がヒントにあることだけ。

## 直し方の原則（3つ）

1. **設問が聞いたことに先に答える。** 詳細はそのあと
2. **初出の語はその場で説明するか、使わない。**
   `workerd` は docs 自身も定義していないので、初級では
   「Workersのランタイム」と呼ぶことにしました。**裏の取れない定義を書かないこと**
3. **補足は補足と分かる形にする。** 行頭に `※` を置いた行は、
   画面上で一段小さく控えめに描かれます。本則のあとの詳細はこの形に分けてください

### 注釈は普通の言葉で着地させる — 別の製品名で説明しない

2026-08-30、初級200問の解説を書き直したあとで**同じ初学者に再プレイさせた**ところ、
12問中5問でまた詰まった。**そのうち4件は、その日に私が書いた文が原因だった。**

```
ai-002  私が足した説明:
        「バインディングとは、WorkerからKVやR2、Workers AIといった
          Cloudflareのリソースを使えるようにする宣言です」
学習者の声:
        「そもそもKVとR2が何なのか分からないから、
          たとえ話のはずが逆に疑問が増えた」
```

**説明のために持ち出した語が、説明対象と同じくらい未知だった。**
`データの保存領域やAIモデルなど` のように、普通の言葉へ着地させる必要がある。

### `※` で補足と示しても、中身が読めなければ救えない

```
ar-013  4ステップの図まで読めていた。そのあとの ※ で
        「デバイスポスチャ」「Zaraz」が説明なしに出て、そこで止まった
学習者の声:
        「むしろここで置いていかれた感じがした」
ar-004  私が書いた ※ に `compatibility_date` が説明なく登場し、
        2つの日付条件が1文に詰め込まれていた
学習者の声:
        「compatibility_dateって何なのかもここでは教えてもらえなかった」
```

**印そのものは効いていた。** 同じ再テストで学習者はこう報告している:

> ※注釈は視覚的に（グレー小文字・図表の後という位置）一貫して本文と区別できており、
> 「これは補足だ」と分かる点は良好でした

つまり `※` は「補足だと分かる」までは果たしている。**だが読み手は読む。**
「読み飛ばしてよい」の印ではないので、補足の中身も初学者の語彙へ落とすか、
その設問から外すかのどちらかにすること。

### 初級解説の書き直しは収束した（実測）

```
1周目（progressive）  詰まり 5/12
2周目（verify）       詰まり 5/12   ← 原則2つを足す前
3周目（verify2）      詰まり 0/6    ← 足したあと
```

2周目まで横ばいだったのは、**私の直し方が間違っていた**から。
足した原則は2つ:

1. **注釈は普通の言葉で着地させる。別の製品名で説明しない**
   （「KVやR2」→「データの保存領域やAIモデルなど」）
2. **`※` は「補足だと分かる」印であって「読み飛ばしてよい」印ではない。**
   補足の中身も初学者の語彙へ落とすか、その設問から外す

3周目でテスターが挙げた解消の中身:

```
ar-013  「ここから先は慣れてきたときに効いてくる話です」の一言で、
        本題との関係が付き「置いていかれる感覚」が解消した
ar-004  compatibility_date を一言定義したうえで
        「新規なら不要 / 古いプロジェクトだけ必要」と結論を1本にまとめた
```

**原則さえ正しければ2回で収まる。** ただし1回では収まらない。
書き換えたら必ずプレイテストへ戻すこと。

### 手本がコーパスの中にある

同じ再テストで `ai-005` は詰まりなしだった。学習者の指摘:

> ai-005ではKV/R2/D1が一言説明つきで表に出ており、
> ai-002で感じた同種の疑問が別の問題では解消されている

**製品名を出すときは、その場で一言添える。** これが基準。

さらに `ar-013` の声は、**補足が本題とどうつながるかを言えば救える**ことも示していた
（「自分がやりたかった『社内の管理画面を守る』話とどうつながるのか分からなくなった」）。
書き出しに「ここから先は慣れてきたときに効いてくる話です」と置くだけで、
読み手は安心して読み飛ばせる。

### 一度直したら、直した本人以外に読ませる

この5件は**掃引では出なかった。** 書いた本人（と同じ役割のエージェント）は
自分が足した語を既知として扱ってしまう。
書き換えたら、必ずプレイテストへ戻すこと。

## やってはいけないこと

- **事実を足さないこと。** この層は裏取り済みです。
  docs に無い説明を「分かりやすくするため」に書けば、それは事実の注入です
- **解説から情報を削るだけで終わらせないこと。** 難しい語を消すのではなく、
  **その場で説明するか、補足へ送る**のが基本です
- **図のマーカー `{{diagram:N}}` を消さないこと**（図が本文から消えます）
- 正解肢の**文字数を大きく変えないこと（±15字以内）**。
  コーパス全体で長さ順位を各25%に揃えてあります

## 出力

```json
[
  { "id": "ag-006", "optionIndex": 0,
    "verdict": "B1 | B2 | B3 | B4 | B5 | ok",
    "verifiedBy": "internal",
    "problem": "初学者がどこで置いていかれるか（1〜2文）",
    "rationale": "ok ならなぜ初学者でも読めると判断したかを1行",
    "edits": [{ "field": "explanation", "value": "..." },
              { "field": "hint", "value": "..." }] }
]
```

`verifiedBy` は `internal` で構いません（事実照合ではないため）。

### 【必須】担当した**全問**を1エントリずつ返すこと

問題が無ければ `verdict: "ok"`、`edits` は空配列。
提出後に自分で被覆を確認:

```bash
node scripts/check-audit-coverage.mjs <あなたの入力> <あなたの出力>
```

- **`src/data/quizzes.json` を直接編集しないこと。** 並列書き込みで壊れます

## 最終メッセージに必ず書くこと

**「何問中いくつ読んで、B1〜B5 / ok が何件だったか」**

実測の詰まり率は 35% でした。**それを目標値として件数を作らないでください。**
0件なら0件と正直に返すのが正しい仕事です。
