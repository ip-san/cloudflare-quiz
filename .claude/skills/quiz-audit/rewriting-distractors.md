# 誤答を書き直すときの手順（書き手向け）

監査側の手順は `SKILL.md`、欠陥の実例は `defect-taxonomy.md`。
**これは書く側が執筆前に読むもの。**

## この手順が生まれた経緯

2026-08-27 に約540肢を書き直したとき、**第1トランシェの186肢中101肢（54%）を破棄した**。
指示が「何を書かないか」（禁止）ばかりで「何を書くべきか」を言っていなかったため、
エージェントが「〜と誤解しやすい」という自己申告文で長さを稼いだ。

効いたのは禁止の追加ではなく、**成果物が満たすべき性質を1つ課すこと**だった:

> 「この誤答に対して、私は反駁の一文を書けるか？
>   書けないなら、それは主張ではなく解説になっている」

これを渡した1体だけが第1ラウンドで自己申告型 0% で、
全体に渡した第2ラウンドは4体とも 0% になった。

## あなたの入力

割り当てられた JSON に、担当する問題が入っている。最低限これらが含まれる:

- `id` / `category` / `question` / `explanation`
- `options[]`: `index` / `text` / `wrongFeedback`
- `correctIndex` / `correctText`
- 書き換え対象の `optionIndex`（長さの指定がある場合は `minLen` / `maxLen` も）

## 絶対に守ること

### 1. 同じ誤りを厚くする。新しい主張を足さない

これが最重要。誤答には既に「その誤りを反駁する」`wrongFeedback` が付いている。
独立した2つめの主張を足すと、**反駁されない誤りが残る**——
これは 2026-08-26 の監査で12件見つけて潰したばかりの欠陥そのもので、
機械検査では検出できない（消えた主張の検出はあるが、増えた主張の検出は無い）。

伸ばすときは、**いま述べている誤った主張そのものを詳しくする**:

- その主張が成り立つとしたら、どういう仕組みで成り立つのか
- その主張に従うと何が起きるのか（誤った帰結）
- その主張が適用される範囲・条件・対象を具体的に述べる

### 1-a. 【最重要】誤答は「学習者が信じうる主張」として書く。信念について語らない

**選択肢の中で「誤解されがち」「勘違いしやすい」「思われがち」と書いてはいけない。**
そう書かれた選択肢は読んだ瞬間に誤答と分かり、4択が成立しなくなる。

誤答は **正解とまったく同じ語り口の、平叙の主張**でなければならない。
「これを信じる人がいる」という外側からの説明ではなく、
**その主張そのもの**を書く。

```
✗ 「`$in` なら配列指定で値以外も除外できると誤解しやすい」
✗ 「`None` に設定しても影響がないと考えられがちである」
✗ 「`{ ignoreVary: true }` で Vary の差異を無視できると誤解されがちである」
      ← すべて自分で「これは誤りです」と名乗っている。選択肢として死んでいる

○ 「`$in` は指定した配列に含まれない値だけを返す否定条件の演算子で、
    `$ne` と同じ働きをしつつ複数の値をまとめて除外できる」
      ← 誤った主張を、正解と同じ顔で言い切っている
```

2026-08-27 の第1トランシェでは、141肢中47肢がこの形になり全て破棄した。
`node scripts/quiz-lint.mjs quality --dry-run` の `option-self-labeling` で検出される。
提出前に必ず自分で確認すること。

**やってはいけない例**（Aが元の誤答、Bが悪い伸ばし方）:

```
A: 「Rule group は IdP が管理するグループそのものを指す」
B: 「Rule group は IdP が管理するグループそのものを指し、かつ1つのポリシーにつき
    1つまでしか適用できない」   ← 2つめの誤りが増えている。反駁されない
```

**良い伸ばし方**:

```
「Rule group は IdP が管理するグループそのものを指し、Okta や Microsoft Entra ID 側で
 作ったグループが Access のダッシュボードにそのまま同期されて表示されるため、
 Cloudflare 側でメンバーを編集することはできない」
     ← 同じ1つの誤解を、仕組みと帰結で厚くしている
```

### 2. 正解の事実を誤答に書かない

もっともらしくしようとして、正解が述べている値・名前・手順をそのまま書くと、
誤答が半分正しくなって消去法が壊れ、誤答を読むだけで正解が確定する。
反転作業では4エージェント全員がこれを踏みかけている。機械検査
（`check-truth-leak.mjs`）で後から照合するが、**書く時点で避けること**。

### 3. 誤答は誤答のままにする

厚くする過程で「実は正しい記述」を書いてしまうと正解が2つになる。
実際 `wr-016` と `as-011` でこれが起きた。
書いた内容が **本当に誤りだと言い切れるか**を1肢ずつ確認すること。
確信が持てないなら、その肢は `skipped: true` で返す（無理に埋めない）。

### 4. 長さは範囲の中でばらけさせる

`minLen` はあくまで下限。全部が `minLen` ちょうどに揃うと、
それ自体が新しい見分け方になる。`minLen` 〜 `maxLen` の中で自然にばらけさせること。

### 5. wrongFeedback が追いつくか確認する

書き直した誤答に対して、既存の `wrongFeedback` が**まだ全体を反駁できているか**を
1肢ごとに判定すること。仕組みや帰結を足したことで反駁が足りなくなったなら、
`wrongFeedback` も一緒に直して提案に含める。

### 6. 事実を捏造しない

Cloudflare の仕様を推測で書かない。誤答に書く「もっともらしい仕組み」は
**実在の概念を誤った形で組み合わせる**のはよいが、存在しない機能名・
存在しない設定値を発明しないこと。判断に迷う場合は
`.claude/tmp/docs/` のキャッシュを grep して確認する。

## 出力

リードから指定された JSON ファイルに次の形で書く:

```json
[
  {
    "id": "wk-004",
    "edits": [
      { "field": "option.3", "value": "書き直した誤答の本文" },
      { "field": "wrongFeedback.3", "value": "必要なら直した反駁" }
    ],
    "skipped": false,
    "note": "何をどう厚くしたか（1行）。skipped なら理由"
  }
]
```

- `field` は `option.N` / `wrongFeedback.N` / `explanation` / `question`
- 触らなかった問題も `skipped: true` で必ず1エントリ返すこと（取りこぼしを数えるため）
- **`quizzes.json` を直接編集しないこと。** 並列書き込みで壊れる。提案だけを返す。

## 自己チェック（提出前に必ず）

各 `option.N` の value について:

1. 長さの指定があれば、その範囲に収まっているか
2. **「誤解」「勘違い」「思われがち」「考えられがち」が入っていないか**（入っていたら書き直す）
3. 元の誤答と**同じ1つの誤り**を述べているか（主張が増えていないか）
4. 正解の値・名前・手順を再掲していないか
5. 書いた内容が本当に誤りか
6. **足した一文を、設問の主語を伏せて読んでも誤りか**
7. 足した語尾が、同じ設問の他の誤答の語尾と重なっていないか
8. `wrongFeedback` がその誤りを全部反駁しているか

## 提出前の機械チェック（必須・省略不可）

提案ファイルを書いたら、**自分で次を実行して 0件であることを確認してから**終わること。

```bash
node - <<'JS'
const fs=require('fs')
const F='.claude/tmp/length-uniform/<あなたの出力ファイル名>.json'
const PAT=/誤解(され)?(が|し)?(ちで|やすい|がち)|勘違い|思われがち|考えられがち|誤認されがち|と誤って|誤りである|間違いである|と(考え|解釈し|みなし|想定し|読ん|思っ|捉え)た場合|と考える。?$|と考える[」）)]/
let bad=0
for(const p of JSON.parse(fs.readFileSync(F,'utf8'))){
  if(p.skipped) continue
  for(const e of p.edits){
    if(!/^option\./.test(e.field)) continue
    if(PAT.test(e.value)){ bad++; console.log('NG', p.id, e.field, e.value.slice(0,60)) }
  }
}
console.log(bad===0 ? 'OK: 自己申告なし' : `NG: ${bad}肢を書き直すこと`)
JS
```

1件でも `NG` が出たら、その肢を**主張として言い切る形に書き直して**から再実行すること。
「〜と誤解しやすい」「〜と考えた場合」は、誤答ではなく**誤答についての解説**であり、
選択肢の位置に置いてはならない。

## 提出前の再読（機械チェックの後に、もう一度）

機械チェックが 0件でも、次の2型は検出されない。**書いた肢を頭から読み直して**確認すること。

### 型1: 誤った前提の上に、真の帰結を乗せていないか

**検算の言い方**: 「この誤答は誤りか」ではなく
**「足した一文を、設問の主語を伏せて読んでも誤りか」**と問うこと。

この作業で最も多かった失敗は、**別の実在プロダクトの正しい説明**を書いてしまうこと。
Durable Objects の設問に Workers KV の仕様を、WAF の設問に Load Balancing の挙動を、
`verified_bot` の設問に `cf.bot_management.score` の値域を書いた例がある。
主語が違うだけで内容は正しいので、「これは誤りか？」と自問すると
主語を見て「誤り」と答えてしまう。

```
前提（誤り）: しきい値を高くするほど誤検知が増え、検知漏れは減る
帰結（真）  : だから誤ブロックを減らしたい場合はしきい値をむしろ上げるべきである
                ← この一文だけを取り出すと docs と一致してしまう
```

足した帰結は、**その誤答の誤った前提と整合していなければならない**。
「本当のこと」を1文でも混ぜると、学習者はそこだけ正しい知識として持ち帰る。

### 型2: 選択肢が自分自身と矛盾していないか

```
前提: `put()` が存在せず書き込み自体ができない
帰結: だから値を更新するには既存のキーを削除して作り直す必要がある
                ← 作り直すこと自体が書き込みなので、前提と両立しない
```

矛盾した選択肢は何を反駁すべきかが定まらない。前提と帰結が同じ世界の話か確かめること。

---

## 「できなかった」報告は成果である

確信が持てない肢は**埋めないこと**。`edits` を出さず、`note` に
「なぜ埋めなかったか」と「docs のどの記述でそう判断したか」を書く。

この作業は毎ラウンド「厚くしようとして docs を確認したら、その誤答は**実は真だった**」
という発見を出している（`tn-005[3]` / `as-007[2]` / `as-011[2]`）。
`as-011` は**正解が2つある状態のまま残っていた本物の欠陥**で、
書き手が手を止めて報告したことでしか見つからなかった。

無理に埋めるより、止めたことを報告するほうが価値がある。

# 対抗馬が0の設問を作り直す（2026-09-15 に約50問で確立）

ここまでは「既にある誤答を**厚くする**」手順。この節は別の仕事で、
**誤答が弱すぎて『本物の対抗馬』が1つも無い設問を作り直す**ときに読む。

「本物の対抗馬」＝**知識のある人がヒント無しでは真剣に迷う肢**。
旧版の誤答が「別製品の説明」「一目で分かる誤り」「架空の機能名」だと、
ヒントをどう直しても設問は易しいままになる。

## 対抗馬の条件は2つある。どちらも要る

1. **ヒントを通過する** … ヒントを読んでも消えない
2. **機能名だけでは切れない** … 製品名・機能名の語義だけで落とせない

**2 を忘れると失敗する。** 実際、ある担当が `survivingGenuine` にヒント耐性だけ書いて
提出し、あとから自分で「名前耐性を見落としていた」と報告してきた（ag-002）。
`survivingGenuine` には**必ず両方**を書くこと。

## 手1: 実在する隣接事実を使う

架空の機能名を作らない。**実在するが、この設問の条件には合わない事実**を誤答にする。
二重正解になりにくく、かつ本当に知らないと切れない。

### 手1a: 実在する数字・名前の「掛かる先」を入れ替える ← 当たりが最も多い

  `kv-009`  1024バイトは metadata 側、25 MiB は値側 → **入れ替える**
  `r2-008`  5 GiB は単発 PUT、5 TiB はマルチパート → **入れ替える**
  `kv-006`  「1秒1回」の制限はキー単位であって名前空間単位ではない → **単位をずらす**
  `ob-008`  7日 / 50億件 / 256KB / 1% を4肢に配り、**超過時の結果の結びつきだけ**を偽にする

値そのものは実在するので捏造にならず、対応関係だけが誤りになる。

### 手1b: 兄弟オプションの振る舞いを付け替える

  `kv-007`  `cacheTtlByStatus` の挙動を `cacheTtl` のものとして書く
  `d1-008`  `batch()` の役割を `exec()` のものとして書く

### 手1c: 以前はそうだったが、今は違うこと

  `dq-013`  `type = "http_pull"` を設定に書く方法は**実在したが現在は非サポート**
  `hw-009`  MySQL 対応が**後追いだった実際の経緯**を使い「PostgreSQLのみ」を誤答にする
  `pl-001`  2025年9月25日より前のレガシーパイプライン（JSONのみ・SQL変換なし）

## 手2: 4肢を同じ語彙・同じ土俵にそろえ、関係を1点だけ偽にする

**「〜の役割は？」「〜の組み合わせは？」という定義型ではこれが主軸になる。**
定義型で同一製品内の事実を誤答にすると**必ず二重正解**になる
（AI Gateway の Guardrails も Vectorize の metadata filtering も実在機能なので、
「これは正しい説明だ」と言えてしまう）。

  `wp-007`  `dispatch_namespaces` と `env.DISPATCHER` を**4肢すべてに持たせた**。
            旧版はこれらを持つのが正解肢だけで、名前の照合だけで解けていた
  `dn-017`  4肢とも「Fullは全プラン・Cloudflareが権威DNS」という**同一の前半を共有**させ、
            Partial 側の説明だけを読み比べさせる
  `ch-013`  4つのトポロジー名を正解肢とそろえ、**Regional の説明だけ**を偽にした
  `pl-002`  Streams / Pipelines / Sinks を全肢に配り、席と名前の対応を知らないと解けなくした

### 定義型で「隣接製品」を使うときは、製品名を出さず動作だけで書く

  `ai-005`（Vectorize とは）… 誤答を Workers AI（埋め込み生成）・AI Search（RAGパイプライン）・
  Agents（状態の永続化と同期）の**動作**で書いた。**結果として「Vectorize＝ベクトル」
  だけでは選べなくなった**（AI Search も内部でベクトル検索をするため）。

**これは「機能名が答えを決めてしまう」型への有効な手でもある。**
`ag-002`（Rate limiting）では、誤答を Dynamic Routing の Rate Limit ノードにした——
**件数を数える点は正解と同じで、超過時の振る舞いだけが逆**なので、
`Rate limiting` という語感では絶対に切れない。

## 捨てる判断ができることが、質に直結する

**強い誤答ほど正解に近づく。** 思いついた候補を捨てた理由を必ず記録すること
（`rejectedStrongerCandidate`）。実際に捨てられた例:

  `wrangler secret bulk` / `wrangler versions secret put`  … どちらも正規の登録方法＝二重正解
  `cacheEverything`                                        … `cacheTtl` がこれを含む
  Apex Proxying / BYOIP                                    … Cloudflare for SaaS の実構成
  Unified Billing のリクエストレート上限                      … 正解と同じ「件数を時間枠で数えて 429」
  Dynamic Routing の Budget Limit ノード                     … **その設問の解説自身が許している**
  「Definitely automated・Likely automated・Not computed」    … **差が1語に縮み、運ゲーになる**

最後の1件は二重正解とは別の棄却理由で、**識別が偶然に依存する形も避ける**。

## 設問文を変えないと直らない型がある

誤答をどう作り直しても直らないものは、**設問文の側**に原因がある。

  **B-1 予告** … 設問文が答えの形や語を先に渡している
      `hw-003`「仕組みの**組み合わせ**」→ 組み合わせの形の肢が正解だけ
      `rt-005`「Traversal Using Relays around NAT」→ 正解肢の中心語を先に渡している
      `bt-001`「3つのBot対策製品の組み合わせ」
  **B-2 前提** … ある立場の誤答を、設問文が成立しなくしている
      `wp-010`「有効化によって**制限される機能**」→「制限は生じない」と述べる肢——
      **本来いちばん強い対抗馬**——が設問文の時点で落ちる

**B-2 の直し方は「開く」こと。**「制限される機能は」→「有効化に伴う影響は」にすると、
対抗馬が成立する。このとき**対抗馬は正解肢と前提を共有している**必要がある
（wp-010 の対抗馬は「`fetch()` は Outbound Worker を経由する」を正解と共有し、
`connect()` の可否だけで分かれる）。

### 例外: `overview` タグの設問は、名前が答えを決めてよい

`overview` タグの35問は6章立ての**製品紹介トラック**で、目的は製品の地図を教えること。
「Vectorize とは何か」は入門として正しい設問であり、細部に作り替えると紹介が消える。
**型Bの判定をする前に `overview` タグを見ること。** 付いていたら設問文は残し、誤答側で直す。

## 根拠の取り方

- **`docRef` は「ファイル名 L行番号」をセットで書く。** 行番号だけでは検証できない。
- **必ず該当ファイルを実際に開くこと。パスを推測しない**（`grep -rn` で本文を探すのが確実）。
- **「その機能は存在しない」を誤答の根拠にしない。**
- **手元の `.claude/tmp/docs/` に無い＝存在しない、ではない。** `fetch-docs.mjs` は
  `topic-config.mjs` に登録されたページしか取れない。**キャッシュの範囲は docs の範囲ではない。**
  この取り違えで、実在する `--preset` フラグを「ドキュメントに記載がない」と
  利用者に見える文章に書いた事故が実際に起きている。

## 正解肢を固定したまま誤答だけ「動作で書く」と、書式の偏りが生まれる（2026-09-15）

`ar-001`（4肢が R2 / Durable Objects / D1 / Workers KV という**製品名だけ**の設問）で、
リードが「製品名を出さず動作だけで書け」と指示したが、担当が**理由をつけて断り、その判断が正しかった。**

**正解肢の本文を変えない制約と両立しない。** 誤答3つだけを動作の文にすると、
**正解だけが製品名という3対1の書式差**が生まれ、「一番形の違う肢を選ぶ」で取れてしまう。
しかも Workers KV の動作を文で書くと、設問文の条件（高頻度読み取り・同一キー・結果整合）の
**言い換えにしかならず型Bが再発する**。

**採った手**: 4肢とも製品名のまま、**最も弱い誤答を差し替える**。
`R2` は名前でも設問文の条件でも二重に切れたので、`Hyperdrive`
（storage-options.md L26 に載る「既存のPostgres/MySQLを速くする層」）に入れ替えた。
対抗馬は `D1`（read-replication.md L14「read replication can lower latency for read queries」）。

### 一般則

**「動作で書く」（手2）は、4肢すべてを動作で書けるときにだけ使える。**
正解肢を固定する掃引では、**書式は4肢でそろえたまま、弱い誤答を差し替える**ほうが安全。
正解肢も動作付きに書き換えてよいなら `correctText: true` で可能だが、
その場合は設問文の言い換えにならないか確かめること。
