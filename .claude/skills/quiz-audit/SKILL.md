# Quiz Audit — 選択肢を書き換えたあとの監査

**いつ使うか**: `src/data/quizzes.json` の選択肢（特に誤答）をまとまった数、書き換えた直後。
1問2問の修正には重い。10問以上、または誤答を「厚くする / 短くする」系の一括作業のあと。

**なぜ要るか**: 2026-08-27 に約540肢を書き直したとき、
**機械検査を全て通過した肢から約5%（29件）の欠陥**が独立監査で見つかった。
機械検査だけでは足りず、しかし人が全肢を読むのも現実的でない。その間を埋める手順。

参照: `defect-taxonomy.md`（欠陥カタログ・実例つき）、
`rewriting-distractors.md`（書き手向けの手順。監査ではなく執筆時に読む）

---

## 引数

- `<baseline-git-ref>`（必須）: **書き換えを始める前**のコミット。
  トランシェごとに走らせる場合も、**毎回キャンペーン全体の基準**を渡すこと。
  トランシェ単位の基準にすると、前のトランシェで作った欠陥を後のトランシェが見落とす
  （2026-08-27 に実際に `cx-003` / `ru-013` を取りこぼした）。
- `--parts N`: 監査エージェントの分割数（既定 3）。1体あたり 150肢を超えないようにする。
- `--report-only`: 修正を適用せず報告のみ。

---

## Phase 0: 機械検査（1コマンド）

```bash
node scripts/quiz-audit.mjs <baseline> --json .claude/tmp/quiz-audit/changed.json
```

差分検査4本（truth-leak / unrefuted-addition / orphaned-refutation / number-drift）と
コーパス全体の `quiz:lint` を決まった順に流し、変更された誤答の一覧を JSON で書き出す。

**候補が挙がったら先に裁定する。** 誤検知が多い検査なので、
`defect-taxonomy.md` の M1〜M8 にある「正常な場合」を確認してから判断すること。

## Phase 1: 独立レビュアーによる監査

`changed.json` を `--parts` で分割し、`general-purpose` エージェントを**同一メッセージ内で**並列起動する。

### 絶対条件

**書いた本人に監査させないこと。** 2026-08-26 の監査で 58件中22件が自己監査になっており、
バッチを組み替え直す羽目になった。新規エージェントを使えば自動的に満たされる。

### プロンプトに必ず入れるもの

1. 「**あなたはこれらを書いた本人ではありません**」
2. `defect-taxonomy.md` の **H1 / H2 を実例ごと**（型の名前だけでは伝わらない）
3. **検算の言い方**:
   > 「この誤答は誤りか」ではなく
   > **「足した一文を、設問の主語を伏せて読んでも誤りか」**
4. 裏が取れない場合は `verdict: "unclear"` とし、**直す提案を出さない**こと
   （`em-009` で裏の取れない反駁を書いて誤った事実を注入した実例がある）
5. **修正案そのものが別の欠陥を作らないこと**。
   `defect-taxonomy.md` 末尾の表を引用し、正解の固有語を含めていないか確認させる
6. 文字数は元の `after` から ±10字以内（長さバランスを壊さないため）
7. **`quizzes.json` を直接編集しないこと**（並列書き込みで壊れる。提案だけを返す）

### 出力契約

```json
[
  { "id": "dl-010", "optionIndex": 1,
    "verdict": "type1 | type2 | unclear",
    "added": "足された部分",
    "rationale": "判定の根拠。docs のどこで裏を取ったか必須",
    "edits": [{ "field": "option.1", "value": "直した誤答本文" }] }
]
```

**担当した全肢を1エントリずつ返させる**（問題が無ければ `verdict: "ok"`）。
そのうえで `node scripts/check-audit-coverage.mjs <入力> <出力>` で被覆を検証する。

最初は「問題があった肢だけ」を返させる契約にしていたが、
**2026-08-28 の掃引で2体が空配列を書いた**。私はこれを「読んでいない」と決めつけたが、
**問い合わせたところ2体とも全肢を読んでおり、当時の契約に忠実に従っただけだった。**
それでも空ファイルは「見ていない」と「問題が無かった」を区別できない。
ファイルの中身そのものを被覆の証拠にする。

### `verifiedBy` — 読んだかより「何を根拠に ok としたか」

問い合わせで**本当の弱点**が出た。1体が正直に申告した:

> 143肢中、docs で裏を取ったのは約20肢。残り123肢は `explanation` との
> 整合性チェックのみ。`explanation` は `wrongFeedback` と同じ書き手が
> 書いている可能性があるので、独立検証になっていない。

**同じ誤解が両方に入っていれば整合してしまう。** 全肢を読んでいても、
裏取りが2割なら「監査した」とは言えない。

各エントリに `verifiedBy: "docs" | "internal"` を必須にし、
`check-audit-coverage.mjs` が両者を分けて数える。
報告は**「N肢を監査した」ではなく「N肢を読み、うちM肢を docs で裏取りした」**。

## Phase 2: 適用

```bash
node scripts/apply-quiz-edits.mjs <proposals.json>
node scripts/quiz-audit.mjs <baseline>     # 修正案が新しい欠陥を作っていないか
```

**修正を適用したら必ず Phase 0 を再実行する。** 修正案が別の検査に引っかかった例が4回ある
（`defect-taxonomy.md` 末尾）。

さらに、**適用した修正案を自分でも「主語を伏せて」読み直すこと。**
監査の修正案は、それ自体が独立レビューを受けていない。
2026-08-27 に `vp-001` の修正案が Workers KV の説明に読めることをこれで発見した。

## エージェント運用の鉄則

### 完了の合図はファイルではない

出力ファイルが現れた時点ではまだ書きかけで、そのあとエージェントが判定を改めることがある。
**`ListAgents` が `idle` を返すか、エージェントの最終メッセージが届いた時点**が完了。

2026-08-27 に3回踏んだ:
- `uni-triage` が `incomplete` → `unclear` に改めた判定を取りこぼし、
  **docs に裏のない主張を反駁に書いて commit した**
- `uni-B3` の提案を `running` 中に適用し、31肢中8肢が途中版だった
- `uni-C3` の提案を適用したあと、2件の実害（H1 / H2）が後から報告された

### 「最終版か」と一度聞く

これだけでエージェント自身の再点検が働く。2026-08-27 に `uni-C3` へ聞いたところ、
`dl-010`（H1）と `kv-006`（H2）の2件を自力で見つけて直してきた。
書いた直後の自己チェックは通っていて、聞かれて読み直したときに気づいている。

### 「できなかった」報告を成果として扱う

確信が持てない肢を無理に埋めさせないこと。
`as-011` は「厚くしようとして docs を確認したら実は真だった」という報告から見つかった、
**正解が2つある状態のまま残っていた本物の欠陥**だった。

## 実測値（2026-08-27、約540肢）

| 工程 | 規模 | 検出 |
|---|---|---|
| 機械検査（Phase 0） | 全肢 | 誤検知が大半。真の検出は数件 |
| 独立監査 第1波 | 422肢 | H1 20件 / H2 2件 |
| 独立監査 第2波 | 154肢 | H1 7件 / H2 1件 |
| 自分での再読（Phase 2） | 監査の修正案8件 | H1 1件 |

**監査の検出率は約5%**、すべて機械検査を通過した肢から出ている。
1体あたり 150肢が上限の目安（それ以上だと精度が落ちる）。

## この監査がカバーしないもの

**書き直した肢を、学習者として UI 上で読むこと。**
機械検査と独立監査を通っても、「選択肢が全部長くて読み切れない」
「誤答のほうが正解より正しそう」といった読み手の体験は測れない。

→ `/playtest` を使う。`node scripts/playtest-coverage.mjs stale` が
**書き換えによってテスト結果が無効になった問題**を deep link 付きで出すので、
そのまま次のバッチの対象になる。

### 実測: プレイテストは監査と別のものを見つける（2026-08-27、18問）

- **H1 は1件も出なかった** — 監査が捕まえきれていた裏付け
- 代わりに **H2 が1件**出た（`ar-016[0]`）。
  「**結果整合性のおかげで**、複数エッジからの同時書き込みでも**常に正確な合計値が得られる**」
  という自己矛盾で、**書き換え作業より前から存在していた**。
  監査は「書き換えた肢」しか見ないので、構造的に射程外だった
- **M2 が1件**出た（`ac-008[2]`）。反駁が2主張のうち1つしか否定しておらず、
  初学者が「正解したのに引っかかりが残った」と報告した。
  機械の M2 検査は語の増減を見るので、**元から2主張だったもの**は挙がらない

**監査は「今回変えたもの」、プレイテストは「今ある状態」を見る。** 射程が違う。

### 既存の誤答を掘るには — `bun run quiz:screen`

差分検査は原理的に既存の欠陥へ届かない。かといって全肢をエージェントに読ませるのは重い
（2026-08-27 時点で未監査は 411問・1,233肢）。**疑わしい順に並べる足切り**を使う。

```bash
node scripts/screen-distractor-risk.mjs --exclude <監査済みの基準> --top 30 \
  --json .claude/tmp/quiz-audit/screened.json
```

拾う指紋は2つだけ:
- **設問にも正解にも出てこない別製品名**を、散文の誤答が名指ししている（H1 の指紋）
- 「できない」と「する必要がある」の同居、
  定義と量化の衝突（`結果整合性` × `常に正確` など）（H2 の指紋）

### 再現率は実測 10%（`bun run quiz:screen:recall`）

既知の陽性30件のうち **3件しか挙がらない**。理由ははっきりしている。

> **H1 の本体は「別製品の振る舞いを*名前を出さずに*説明している」ことで、
> スクリーニングが見ているのはその逆（名前が出ている場合）だけ。**

```
dq-001[2]「各レプリカが非同期に同期する結果整合性モデルのため…」← KV を名指ししない
wf-001[1]「応答しなくなったオリジンを自動的に切り離す」        ← Load Balancing を名指ししない
d1-010[0]「途中の文が失敗すれば以前に成功した文も含めロールバック」← batch() を名指ししない
```

**H1 は語彙では拾えない。読み手が要る。**
この道具が実際に効くのは H2（定義と量化の衝突）で、`ar-016[0]` を検出できた。

したがって:
- **上から潰しても「全数を見た」根拠にはならない。** 90%が残る
- 既存の誤答を本気で潰すなら、スクリーニングではなく**全肢をレビュアーに読ませる**しかない

### 全数掃引（`build-audit-batches.mjs`）

```bash
node scripts/build-audit-batches.mjs --parts 12 --out .claude/tmp/quiz-audit --exclude <監査済みの基準>
```

肢数で均等に分割して `sweep-partN.json` を書き出す。
**問題数ではなく肢数で割る**こと（1問あたりの誤答数が2〜3とばらつき、
問題数で割ると担当量が2割ずれる）。

レビュアーには `sweep-prompt.md` を読ませる。差分監査と違い `before` が無いので、
「足された一文」ではなく**誤答の全文**を読ませる手順になっている。

規模の実測（2026-08-28）: 誤答2,268肢のうち、書き換えで監査済みなのは556肢。
**残り1,712肢・746問が一度も監査されていない。**
（当初 1,233肢と見積もったが、これは「触っていない問題」しか数えておらず、
**触った問題の中の未変更肢**を落としていた。基準からの差分で数えるときの典型的な取りこぼし。）
- スクリーニングは「まず十数肢だけでも潰す」ための入口

**指標を変えたら `bun run quiz:screen:recall` を流し直すこと。**
既知の陽性リストはこの harness の中にあり、新しく見つかったら追記する。

### 適合率も測った — この回は 0/15

2026-08-28 に上位15肢を独立監査に回した結果、**真の陽性は0件**だった
（H1 判定が1件出たが、監査が**主語を書き換えて作った「真の一文」**に基づくもので、
`defect-taxonomy.md` の「H1 の境界」に照らして採らなかった）。

**再現率10% / 適合率0% で、H1 の道具としては成立していない。**
H2（定義と量化の衝突）で `ar-016[0]` を検出できた1件が、現時点で唯一の実績。

この事実を書いておかないと、次に触る者が
「スクリーニングを回したから既存分も見た」と誤読する。

プレイテストのプロンプトには、`defect-taxonomy.md` の H1/H2 を
**学習者に伝わる言葉**で入れること（「これは本当なのか嘘なのか分からない、
と感じた文があれば報告してください」）。型の名前では伝わらない。
