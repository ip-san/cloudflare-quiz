# 正解・解説・設問文を全数監査する — レビュアー向け手順

誤答の掃引（`sweep-prompt.md`）とは**探すものが違う**。

誤答の欠陥は「学習者が選ばなければ実害が小さい」が、
**正解と解説は学習者が真実として読む。** 誤りがあれば、そのまま知識になる。

## 入力

`targets[0]` に:

- `question` / `correctText`（正解の選択肢）/ `explanation` / `hint`
- `wrongFeedbacks[]` — 各誤答とその反駁（**正解と矛盾していないかを見るため**に添えてある）
- 問題側: `id` / `category` / `difficulty` / `referenceUrl`

---

## 探すもの

### C1. 正解が docs と食い違っている

**最も重い欠陥。** 手順・順序・条件が docs と逆になっていることがある。

```
cb-018  正解「誤検知が疑われる場合は、**まずSaaSプラットフォーム側での実際の状態を確認し**…」

docs（troubleshoot-casb）の手順:
  1. Review finding details — Carefully examine the evidence provided in the finding.
     **An object's status in the SaaS platform may not be accurate.**
  2. Report the issue
  3. Hide the finding

→ 第1手順は「**finding の証拠を精査する**」で、
  「SaaS 側は不正確な場合がある」は**そちらを信用するなという注意喚起**。
  正解文はこれを「SaaS 側を確認する理由」として逆向きに使っていた。
```

**「だいたい合っている」では足りない。** 手順の**順序**、条件の**向き**、
「〜する必要がある」と「〜してもよい」の別まで docs と照合すること。

### C2. 解説の数値・事実が docs と食い違っている

```
as-018  explanation「…Business 500・API Shieldなしの **enterprise 500**」
        docs（api-shield/plans）「Enterprise without API Shield | **3000**」
        同じ設問の wrongFeedback は正しく「3,000」と書いていた
```

**解説は先に読まれる**ので、ここが誤っていると実害が大きい。
同じ設問の他の層（反駁）と食い違っていないかも見ること。

### C3. 解説が正解と矛盾している / 反駁が正解と矛盾している

```
ar-018  正解「課金軸が**リクエスト数**とCPU時間であるため…」
        反駁「…**まとめること自体がコスト最適化にはなりません**」
              ← 正解が「リクエスト数は課金軸」と言っているのに否定している
```

`wrongFeedbacks` を添えてあるのはこのため。**正解と並べて読むこと。**

### C4. 設問が答えを一意に決めていない

- 設問の条件では複数の選択肢が成り立つ
- 「正しいものはどれですか」なのに、正解以外にも正しい記述がある
  （誤答側の問題だが、設問の書き方で防げる場合がある）
- 設問文自体に誤った前提が含まれている

### C5. ドキュメント改定で正解が古くなっている

docs が更新され、正解が現在の仕様と合わなくなっていることがある。
過去に `wr-016`（正解が2つになっていた）、`ag-016`（正解が事実誤りに）で実際に起きた。

**`referenceUrl` 先の記述が正解と一致するかを、必ず現物で確認すること。**

## 判定の材料

- ローカルキャッシュ `.claude/tmp/docs/` を grep すること
- `<WranglerNamespace>` を含むページはサブコマンド一覧がビルド時生成でソースに実体が無い。
  キャッシュだけで「そのサブコマンドは無い」と判定しないこと
- **裏が取れない場合は `unclear`。修正案を出さない。**
  裏の取れない主張を書いて誤った事実を注入した実例（`em-009`）がある

**この層は `internal` 判定を認めません。** 正解と解説は
「設問内の整合性」では検証できません（同じ書き手が書いているため）。
**必ず docs に当ててください。**

### `verifiedBy: "standard"` — Cloudflare docs に原理的に載らない事実

HTTP・DNS・TLS などの **Web 標準そのもの**についての事実は、
Cloudflare docs には書かれないことがあります。この場合に限り
`verifiedBy: "standard"` を使ってください。

```
ru-010  正解「301(恒久的)と302(一時的)はリクエストメソッドがPOSTからGETへ
             ダウングレードされることがあるのに対し、307と308はメソッドを保持する」
        → RFC 7231 §6.4.2/6.4.3（301/302 は "a user agent MAY change the request
          method from POST to GET"）と RFC 7231 §6.4.7 / RFC 7538 §3（307/308 は保持）
        → Cloudflare docs には載らない。`standard` で裏取り
```

**条件は2つ:**

1. **標準の名前と該当箇所を `rationale` に必ず書くこと**（「RFC 7231 §6.4.7」など）。
   「よく知られた仕様だから」は不可です
2. **Cloudflare 固有の挙動には使えません。** プラン別の上限、既定値、
   製品の手順などは必ず `docs` です

裏が取れない場合は `unclear` のままにしてください。

---

## 修正案を出すときの注意

正解や解説を直すと、**設問全体の整合が崩れやすい**:

- 正解を直したら、**誤答がまだ誤りのままか**を確認する（正解が変わると誤答が真になりうる）
- 正解を直したら、**各反駁がまだ成立するか**を確認する
- 解説を直したら、`{{diagram:N}}` のマーカーを**消さない**こと（図が本文から消える）
- 正解の**文字数を大きく変えない**（コーパス全体で長さ順位を各25%に揃えてある。±15字以内）

---

## 出力

```json
[
  { "id": "cb-018", "optionIndex": 1,
    "verdict": "C1 | C2 | C3 | C4 | C5 | ok | unclear",
    "verifiedBy": "docs | standard",
    "problem": "何が問題か（1〜2文）",
    "rationale": "判定の根拠。docs のどのファイルのどの記述かを必ず書く",
    "edits": [{ "field": "option.1", "value": "直した正解本文" },
              { "field": "explanation", "value": "直した解説（{{diagram:N}} を残すこと）" }] }
]
```

### 【必須】担当した**全問**を1エントリずつ返すこと

問題が無ければ `verdict: "ok"`、`edits` は空配列、
`rationale` に「docs のどこと照合して ok としたか」を1行。

提出後に自分で被覆を確認してください:

```bash
node scripts/check-audit-coverage.mjs <あなたの入力> <あなたの出力>
```

**1問でも欠けていれば差し戻します。**

- **`quizzes.json` を直接編集しないこと。** 並列書き込みで壊れる

## 途中で終わる場合

読み切れないと判断したら、**そこで止めて正直に報告してください。**
読んだ分だけを出力し、「何問まで読んだか」を書けば、リードが残りを割り直します。
**無理に埋めたり、空で返したりしないこと。**

## 最終メッセージに必ず書くこと

**「何問中いくつ読んで、C1/C2/C3/C4/C5/ok/unclear が何件だったか」**

この層は全問 docs 裏取りが原則です。当てられなかった問があれば、その数も書いてください。
