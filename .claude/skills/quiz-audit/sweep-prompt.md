# 既存の誤答を全数監査する — レビュアー向け手順

差分監査（`quiz-audit.mjs`）は「今回書き換えた肢」しか見ない。
これは**一度も監査されていない既存の誤答**を全数読むための手順。

## 入力

`targets[]` の各要素が監査対象の誤答:

- `optionIndex` / `text`（誤答の本文）/ `wrongFeedback`（その誤答への反駁）
- 問題側: `id` / `category` / `difficulty` / `question` / `correctText` / `explanation` / `referenceUrl`

**差分ではないので `before` は無い。** 「足された一文」ではなく、
**誤答の全文を読んで**、その中に問題のある文が無いかを見る。

---

## 探すもの

### H1. その誤答の中に「そのまま読んで真である文」が混じっていないか

**この作業で最も多い欠陥。** 誤答を「もっともらしく」するために、
書き手はその分野で実際に起きることを書いてしまう。

実例（すべて実際に修正した）:

| 設問の主語 | 誤答に混じっていた真の記述 |
|---|---|
| `dq-001` Durable Objects | **Workers KV** の結果整合性 |
| `wf-001` WAF | **Load Balancing** のヘルスチェック |
| `wp-001` Workers for Platforms | **Workers Builds** の CI/CD |
| `d1-010` `prepare().run()` | **`batch()`** のロールバック挙動 |
| `sl-016` Always Use HTTPS | **Automatic HTTPS Rewrites** の書き換え |

`wrongFeedback` が誤答の主旨を否定しても、**その一文だけは否定されずに残る**。
学習者はそこだけ正しい知識として持ち帰る。

#### 【最重要】H1 の境界 — これを外すと全ての誤答が H1 になる

判定は必ずこの順で:

1. その文を **そのまま（主語を含めて）** 読む → **真なら H1**
2. 主語を伏せて読むと真 → H1 の疑い。**ただし `wrongFeedback` が
   その能力を正しい持ち主へ名指しで再帰属していれば `ok`**
3. **主語を書き換えれば真** → **H1ではない。`ok`。**

3 を H1 に含めると、誤答の定義そのものになってしまう。

採らなかった実例:

```
tn-013[0]「レプリカはラウンドロビンやハッシュベースのルーティングによる
          インテリジェントなトラフィック分散をサポートしており…」

  ✗ 「Load Balancer の挙動をレプリカに貼り替えている」という理由づけは不可。
     文中の主語は一貫して「レプリカ」で、そのまま読めば偽。
     さらに wrongFeedback が「インテリジェントな分散が必要な場合は
     Cloudflare Load Balancer を使用します」と正しい持ち主へ再帰属している → ok
```

### H2. 誤答が自分自身と矛盾していないか

```
前提: `put()` が存在せず書き込み自体ができない
帰結: だから値を更新するには既存のキーを削除して作り直す必要がある
      ← 作り直すこと自体が書き込みなので、前提と両立しない

ar-016[0]「結果整合性のおかげで、複数エッジからの同時書き込みでも
          常に正確な合計値が得られる」
      ← 結果整合性は定義上「常に正確」の否定
```

矛盾した誤答は、内容を知らなくても矛盾だけで外せてしまう。

### H3. その誤答は本当に誤りか（正解が2つになっていないか）

docs を確認したら**誤答が真だった**というケースが実際にある
（`as-011[2]` は正解が2つある状態のまま残っていた）。
**確信が持てないものは `unclear`。直す提案を出さないこと。**

**見分け方: `wrongFeedback` が誤答を半ば認めていないか。**
誤答が真だと、反駁は正面から否定できず譲歩の形になる。

```
wa-010[2] 反駁「…**JavaScript 無効化自体は必須条件ではありませんが**、
              選択肢としては前提条件を正しく説明していません」
       → docs の Prerequisites は CDN / プロキシ済み DNS / クッキー有効化の3点のみ。
         誤答の主張は真で、反駁はそれを認めたうえで
         「前提条件の説明として不適切」という別の理由で誤答扱いしていた
```

反駁に「**〜ではありませんが**」「**〜自体は正しいものの**」「**厳密には〜だが**」が
出てきたら、その誤答は誤答になっていない。**必ず報告すること。**

### M2. 反駁が誤答の主張を全部否定しているか

誤答が2つ以上の主張を含むのに、`wrongFeedback` が1つしか否定していない場合、
**否定されなかった主張だけが誤解として残る**。

```
ac-008[2] 誤答「Rule group は IdP が管理するグループそのものを指し、
              **IdP側で作成すると Access へ自動的に同期される**ため、
              Access側で独自に作成することはできない」
          反駁「Rule group は Access 側で作成する独自の概念であり、
              IdP が管理するグループとは別物です」
          → 自動同期の主張が否定されないまま残っていた
```

初学者が「正解したのに引っかかりが残った」と報告して見つかった型。

## 判定の材料

- ローカルキャッシュ `.claude/tmp/docs/` を grep して裏を取ること
- `<WranglerNamespace>` を含むページはサブコマンド一覧がビルド時生成でソースに実体が無い。
  キャッシュだけで「そのサブコマンドは無い」と判定しないこと
- **裏が取れない場合は `unclear`。修正案を出さない。**
  `em-009` で裏の取れない反駁を書いて誤った事実を注入した実例がある

---

## 修正案を出すときの注意

**修正案そのものが別の欠陥を作らないこと。** 過去に6回起きている:

- 正解の固有語（識別子・数値・製品名）を修正案に持ち込んだ（`pl-002` / `d1-010`）
- 差し替えた文が今度は真になった（`ob-007`）
- 差し替えた文が別製品の説明に読めた（`wp-001` は Cloudflare Pages、`vp-001` は Workers KV）

修正案を書いたら、**それ自体に上の H1 判定（3ステップ）をかけること。**

文字数は元の `text` から **±15字以内**（選択肢の長さバランスを保つため。
コーパス全体で正解の長さ順位を各25%に揃えてある）。

## 出力

```json
[
  { "id": "ar-016", "optionIndex": 0,
    "verdict": "H1 | H2 | H3 | M2 | ok | unclear",
    "verifiedBy": "docs | internal",
    "problem": "何が問題か（1〜2文）。ok なら省略可",
    "rationale": "判定の根拠。verifiedBy が docs なら、どのファイルのどの記述かを書く",
    "edits": [{ "field": "option.0", "value": "直した誤答本文" },
              { "field": "wrongFeedback.0", "value": "必要なら直した反駁" }] }
]
```

### 【必須】`verifiedBy` — 何を根拠に判断したか

- **`"docs"`**: `.claude/tmp/docs/` の実ファイルに当たって確かめた。
  `rationale` にファイル名と該当記述を書くこと。
- **`"internal"`**: 設問内の `correctText` / `explanation` との整合性だけで判断した。

**`internal` は独立検証ではありません。** `explanation` は `wrongFeedback` と
同じ書き手が書いている可能性があり、**同じ誤解がそのまま両方に入っていれば整合してしまいます。**

`internal` で判断すること自体は禁じません。全肢に docs を当てるのは現実的でない場合があり、
「そのまま読んで明白に偽」な肢まで grep する必要はありません。
**禁じるのは、`internal` で見たものを `docs` と申告することです。**

### ただし、次に該当する肢は必ず `docs` に当てること

1. **数値を含む肢**（上限・件数・秒数・サイズ・プラン別の値）
2. **「〜のみ」「〜だけ」「一切〜ない」「必ず」「常に」といった断定を含む肢**
3. **固有名詞（製品名・クラス名・API名・設定名）を挙げている肢**
4. **反駁に「〜ではありませんが」「〜自体は」「厳密には」「別の観点」が含まれる肢**

これらは `internal` では判定できません。**裏取り0肢のバッチは監査として成立しません。**
2026-08-28 の掃引では、バッチ間の裏取り率が 0〜100% とばらついた。
0% のバッチは追加パスを依頼して埋め直している。

2026-08-28 の掃引で、1体が正直に申告しました:

> 143肢中、docs で裏を取ったのは約20肢。残り123肢は `explanation` との
> 整合性チェックのみ。独立検証にはなっていません。

この申告があったおかげで「143肢を監査した」ではなく
**「143肢を読み、うち20肢を docs で裏取りした」**と正しく記録できました。
読んだかどうかより、**何を根拠に ok としたか**のほうが重要です。

### 【必須】担当した**全肢**を1エントリずつ返すこと

問題があった肢だけではなく、**`targets` に挙がっている全ての肢**について
1エントリを返してください。問題が無ければ `verdict: "ok"`、`edits` は空配列、
`rationale` に「何を確認して ok としたか」を1行。

**これは形式の都合ではありません。**
2026-08-28 の掃引で、2体が143肢の担当に対して**空配列を書き、報告もせず終了**しました。
手順書には「何肢読んだか必ず報告せよ」と書いてありましたが、
**報告しないという形で破られると検出できません。**
自己申告に頼る検査は、申告しない相手には効きません。

ファイルの中身そのものを被覆の証拠にします。提出後、リードが次を実行します:

```bash
node scripts/check-audit-coverage.mjs <あなたの入力> <あなたの出力>
```

**担当肢が1つでも欠けていれば未完了として差し戻し**、担当を割り直します。

- **`quizzes.json` を直接編集しないこと。** 並列書き込みで壊れる

## 途中で終わる場合

読み切れないと判断したら、**そこで止めて正直に報告してください。**
読んだ分だけを出力し、最終メッセージに「何肢まで読んだか」を書けば、
リードが残りを割り直します。

**無理に埋めたり、空で返したりしないこと。**
この掃引の目的は「どこまで見て、どこから先は見ていないか」を言えるようにすることです。
検出ゼロという結果自体は正常な可能性があります。**見ていないことを検出ゼロと呼ばないでください。**

## 最終メッセージに必ず書くこと

**「何肢中いくつ読んで、H1 / H2 / H3 / M2 / ok / unclear が何件だったか」**

**および「そのうち何肢を docs で裏取りしたか」。**
裏取りが一部にとどまるなら、そう書いてください。それは失敗ではなく、
台帳に正しく残すために必要な情報です。
